# カフェ経営シミュレーター 構想・実現可能性まとめ

> 目的：「Coffee Inc 2 的な本格経営戦略」×「街の俯瞰マップから店舗に立ち寄る画面遷移」×「Supermarket Simulator 的に店内に入って歩き回り・お客さんと話せるモード」を実現できるか、どう整理するかをまとめる。
> ステータス：**要件定義フェーズ（方向性すり合わせ完了 / 第1スライス設計へ）**

---

## ★ 確定した方向性（2026-06-28 すり合わせ）

| # | 論点 | 決定 |
|---|---|---|
| 視点 | プレイヤーの立ち位置（背骨） | **俯瞰↔店内3人称を行き来。** 立ち上げ期（立地選び・内外装）は俯瞰、運営は3人称で現場、軌道に乗れば**店長に委任**して経営者目線へ。**一人称ではなく3人称。** |
| 事務所 | バックオフィス | **事務所あり。** Coffee Inc 的に採用・新メニュー開発・経営判断をそこで行う。 |
| 時間 | 進行方式 | **ハイブリッド。** 店内に降りている間はリアルタイムで客が動く、街に上がると日次サマリーで早送り。 |
| 世界観 | 舞台 | **実在都市ベースのリアル志向。** ただしビジュアルは**原神(Genshin)テイスト**を目標（あれより少しだけ簡素でOK）。キャラはやや簡素、街並み・世界グラフィックを寄せる。 |
| フック | 差別化の軸 | **全部入れる：** ①常連が育つ人間ドラマ ②SNSでバズる現代性 ③コーヒーの専門性 ④街づくり。 |
| 経営 | Coffee Inc 要素 | **フル実装志向：** 不動産購入・投資・ローン・競合・設備導入・財務・人事 等すべて。 |
| 客 | ペルソナ駆動 | **経営方針で来る客層が偏る。** 学生／家族連れ／サラリーマン等のデモグラ。利用目的（勉強・長居・サッと一杯）も差。 |
| 公開 | ゴール | **まず自分用 → 改善して世に出せるレベルまで。** |
| 技術 | プラットフォーム | **ブラウザ + Three.js（推奨・要最終確認）。** URLで即プレイ＝高速イテレーション。将来Steam等で本気化するならGodot移植検討（シミュ層は再利用）。 |

### アート方針の現実ライン（重要・正直）
- **「原神レベルのフィデリティ(作り込み)」は最初からは出せない**（AAA・数百人・数年規模の産物のため）。狙うのは**「原神っぽいアートの"方向性"」**。
- 進め方：**グレーボックス（簡素な箱の街と人）で"遊べる"状態を先に作る → 面白さ確認 → スタイライズ3Dアセットを段階的に着せる。**
- これが成立するのは、**表示層とシミュ層を分離**しているから（見た目は後から育てられる）。

---

## 0. 結論（先に要点）

- **実現は可能。ただし"フル3D一人称＋超本格経営"を最初から全部やると超大型開発になる。** 段階的に作るのが現実的。
- 鍵は **「経営シミュ層（数字・ロジック）」と「見せ方層（マップ表示／店内ウォークスルー）」をきっぱり分離する** こと。中身（シミュレーション）が動いていれば、見た目は後からいくらでも乗せ替えられる。
- 店内ウォークスルーは **「フル3D一人称」より先に「見下ろし／斜め見下ろし(2.5D)で歩ける」版** から作ると、体験（中に入る・客が寛いでる・話せる）を早く確認できてリスクが低い。
- まず決めるべき大きな分岐は **①プラットフォーム（ブラウザ or Unity/Godep等のエンジン）** と **②店内の3D本気度（フル3D / 2.5D見下ろし）** の2つ。

## 1. リファレンス分析（事前情報）

### 1-1. Coffee Inc 2（参考：経営の"深さ"）
本格的な**経営戦略・タイクーン系**。画面は3Dウォークスルーではなく、**メニュー・ダッシュボード・表計算的UI中心**。深さの正体は以下：

| 領域 | 中身 |
|---|---|
| 出店戦略 | 立地選び、世界の実在都市（SF, NY, 東京, 大阪, ロンドン, パリ 等）へ展開、複数通貨(USD/EUR/JPY/GBP) |
| 店舗運営 | レイアウト・内装・音楽・香りでアンビエンス最適化、設備購入 |
| 人事 | 採用・教育・モチベ管理・店長委任、突発トラブル対応 |
| 経営/財務 | 損益計算書・貸借対照表・キャッシュフロー、配当 |
| 経営上層 | COO/CFO/CTO/CMO等のC人材、ストックオプション、取締役会、IPO、買収、投資銀行 |
| サプライ | 世界から豆を調達、自社農園で栽培・収穫・品質管理（farm to cup） |
| 競争 | ライバル企業とシェア争い |

**→ 学び：Coffee Inc の"おもしろさ"は3Dグラフィックではなく『意思決定の深さと数字の手応え』。ここはブラウザでも完全に再現可能な領域。**

### 1-2. Supermarket Simulator（参考：店内ウォークスルー）
**一人称**で店を運営する箱庭シム。

- 店をデザイン（棚の配置・通路・効率と見た目）
- PCで発注 → 段ボール開封 → 倉庫に整理 → 棚・冷蔵・冷凍に陳列
- レジ：商品スキャン・現金/カード決済・客の満足
- リアルタイム市場：安く仕入れ、売値を決める
- 客が店内を歩き、万引きもいる（防犯カメラ・警備員）
- 利益で店を物理的に拡張・内装アップグレード
- 最大4人協力プレイ

**→ 学び：店内に入る没入感の核は『客が動く・棚に物がある・自分が作業する手触り』。3Dだが、必ずしもフォトリアルである必要はない。**

### 1-3. Moonlighter（参考：2層をどう繋ぐか）
**街マップ↔店内**を行き来する設計の好例。

- 街マップ：自分の位置・各店・クエストを俯瞰
- 店内：自分の店の中を歩き、棚に商品を置き、レイアウトや内装を改装・拡張

**→ 学び：ユーザー要望の『街を俯瞰→店に立ち寄る→中に入る』は、すでに実績のある王道の画面遷移パターン。設計として無理がない。**

## 2. ユーザー要望の分解

| # | 要望 | 種別 |
|---|---|---|
| A | 本格的な経営戦略・カフェシミュレーター（Coffee Inc 級の深さ） | シミュ層 |
| B | 街を俯瞰し、カフェに立ち寄って店舗ごとの状況を把握する画面遷移 | マクロ表示層 |
| C | 店舗の中に入れる（一人称でなくてOK）＝Supermarket Sim 的ウォークスルー | ミクロ表示層 |
| D | 店内でお客さんと話せる／客が寛ぐ様子が見える | ミクロ表示層 |

ポイントは **A（数字の深さ）と C/D（3D的没入）は"別レイヤー"** だということ。混ぜずに作る。

## 3. アーキテクチャ整理（最重要）

```
┌─────────────────────────────────────────────┐
│  ① シミュレーションコア（見た目に依存しない頭脳） │
│  ・時間/日付の進行（ターン or リアルタイム）      │
│  ・経済モデル：需要・価格・原価・利益・財務諸表    │
│  ・店舗データ：立地/レイアウト/設備/スタッフ      │
│  ・客モデル：来店・好み・満足度・行動             │
│  ・セーブ/ロード（状態は全部ここに集約）          │
└───────────────┬─────────────────────────────┘
                │ 同じ状態を2つの「見せ方」が読む
      ┌─────────┴──────────┐
      ▼                    ▼
┌──────────────┐   ┌──────────────────────┐
│ ② マクロ表示  │   │ ③ ミクロ表示（店内）   │
│ 街マップ/一覧 │   │ 店内ウォークスルー     │
│ ダッシュボード│   │ 客が歩く/話す/寛ぐ     │
│ 経営の意思決定│   │ 陳列・レジ・接客       │
└──────────────┘   └──────────────────────┘
```

**この分離が効く理由：**
- シミュ層さえ正しく動けば、マクロ表示だけで"遊べる経営ゲーム"が先に完成する（早期に面白さ検証できる）。
- 店内ウォークスルー(③)は後から段階的に乗せられる。2.5D→フル3Dの差し替えも、③だけ作り替えればよい。
- セーブやバランス調整がコア1箇所で完結する。

## 4. 技術選択（事前情報：選択肢マトリクス）

「中に入って歩く」をどう実現するかで土台が変わる。

| 観点 | A. ブラウザ(Three.js / Babylon.js) | B. ブラウザ2.5D(Phaser/Canvas) | C. エンジン(Unity / Godot) |
|---|---|---|---|
| 配布 | URL1つ。即遊べる | URL1つ。即遊べる | DL必要(Webビルドは重い) |
| 店内3D | ◎ フル3D歩行可 | △ 斜め見下ろしの疑似3D | ◎ 最も本格的 |
| 開発難度 | 高（3D実装・最適化） | 中 | 中〜高（要エンジン学習） |
| 初期表示/容量 | 軽い（段階読込可） | 最軽量 | 重い（空でも数MB〜25MB） |
| 物理/当たり判定 | Three=自前 / Babylon=内蔵 | 自前(簡易) | 内蔵で強力 |
| アセット必要量 | 多（3Dモデル/テクスチャ） | 中（スプライト/タイル） | 多 |
| AIとの相性(本リポで生成) | ○ コードで完結 | ◎ コードで完結・軽い | △ エディタ操作前提で相性弱め |
| この案の推し所 | 没入感とWeb即時性の両立 | 最速で"中に入れる"体験を出せる | 将来フル本格化するなら最強 |

**現時点の推奨：ブラウザ前提。**
- 経営シミュ＋マクロ表示：素のWeb(HTML/JS or 軽量フレームワーク)で十分。
- 店内：**まず2.5D見下ろしで"歩いて客と話せる"を実装 → 手応えが出たらThree.js/Babylon.jsでフル3Dへ昇格**、という段階法が最もリスクが低い。
- ※「最初からPC向けフル3D・本格没入」が絶対なら Unity/Godot 案に倒すべき（その場合は成果物の形が変わる＝要相談）。

## 5. データモデル（コアの主要エンティティ・素案）

- **World**：日時、経済指標、トレンド、通貨レート
- **City / District**：エリア、地価、人通り、客層
- **Store**：立地、レイアウト(グリッド)、設備、内装Lv、評判、在庫
- **Equipment**：エスプレッソマシン等（性能/故障/メンテ）
- **MenuItem / Recipe**：原価・価格・人気・必要設備
- **Supply / Bean**：豆の産地・品質・在庫・価格変動（将来：自社農園）
- **Staff**：スキル、給与、モチベ、シフト、店長委任
- **Customer**：好み、予算、満足度、滞在/行動状態（来店→注文→着席→寛ぐ→退店）
- **Finance**：売上/原価/人件費/家賃、PL・BS・CF
- **Company**：資金、ブランド、株式、（将来：C人材・IPO・買収）
- **SaveState**：上記すべてのスナップショット

## 6. 段階的ロードマップ（スコープ階段）

> 「全部入り」を一気にやらず、各フェーズで"遊べる状態"を作る。

- **フェーズ0：シミュコアMVP（数字だけで回る）**
  1店舗・1日サイクル・客の来店/注文/利益・簡単な財務。UIは最小。
- **フェーズ1：マクロ表示**
  街マップ＋店舗一覧＋ダッシュボード。出店・価格・メニュー・スタッフの意思決定。複数店舗。
- **フェーズ2：店内ウォークスルー（2.5D）**
  自分の店に"入る"。客が歩く・席で寛ぐアニメ。クリックで客と会話、注文/満足が見える。陳列やレイアウト編集。
- **フェーズ3：経営の深掘り（Coffee Inc 寄せ）**
  サプライチェーン（豆調達/品質）、財務諸表の精緻化、ライバル競争、複数都市・通貨。
- **フェーズ4：没入強化（任意）**
  店内をThree.js/Babylonでフル3D化、C人材/IPO/自社農園など上級経営要素。

**各フェーズ末で必ず「触って面白いか」を確認 → 次へ。**

## 7. 難所・リスク（正直に）

1. **店内フル3Dのアセット**：3Dモデル/テクスチャ/アニメは制作コストが高い。フリー素材＋簡易表現で割り切る前提が必要。
2. **2層の状態同期**：マクロで決めた事が店内に反映され、店内の操作がマクロに返る…の整合性。→ コア1箇所集約で対処。
3. **経済バランス調整**：「儲かりすぎ/詰む」を避ける数値調整は地味に重い。早期からプレイテスト。
4. **スコープ膨張**：Coffee Inc は何年もかけた製品。"どこまでやるか線引き"を都度握るのが最重要。
5. **パフォーマンス**：多客×多店舗×3Dはブラウザだと重くなりうる。客数上限・LOD・簡易AIで制御。

## 8. 次に決めたい論点（ユーザー確認事項）

1. **プラットフォーム**：ブラウザ(URLで即)か、本格3D前提でエンジン(Unity/Godot)か。
2. **店内の3D本気度**：まず2.5D見下ろしで体験を出す → 後でフル3D昇格、でOKか。最初からフル3D必須か。
3. **遊ぶ環境**：スマホも対象か、PC中心か。（フル3D一人称＝PC寄り）
4. **最優先で見たい体験**：「経営の数字の深さ」と「店内に入って客と話す没入」、最初に形にすべきはどちら？
5. **ボリューム/ゴール**：エンドレス経営か、目標達成型（◯年で売上◯/全国制覇 等）か。
